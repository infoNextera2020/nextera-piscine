# Quest review persistence seam 001

Status: source-only repository/service contract with injected tests. No PostgreSQL adapter, registered schema, endpoint, queue consumer, runtime connection or live persistence is provided. `packages/db/operations/quest-reviews.ts` is imported directly by its tests; it is not added to package exports or consumed by staff UI. No SQL draft is necessary for this bounded milestone; ownership, privileges and schema design remain review work.

`prepareQuestReview` resolves the authenticated subject to the current active cohort actor through the repository, requires learner ownership, and freezes one initial review cycle before returning its five ordered question IDs. It persists the exact content/evidence versions and digests, bank version/digest, sampler/rubric versions and review-policy snapshot. Existing cycles are loaded without invoking a sampler, including after an uncertain result or concurrent reload. Changes to evidence, policy, bank or rubric fail closed; this slice offers no replacement cycle or implicit review retry.

Initial peers are chosen automatically from the explicitly ranked, eligible active cohort learner pool using the existing nonreciprocal domain contract. Completed peer receipts lead to automatic initial mentor allocation from active eligible cohort operators/admins. There is no separate mentor role and an unrelated admin cannot approve. Self review, cross-cohort review, peer-issued mentor approval, stale evidence and wrong assignments are rejected. An unavailable peer or mentor leaves the cycle pending; it does not grant mastery or bypass review. The configured peer gate must be `submitted`; a positive peer verdict is not substituted for completed peer review. The peer count remains required configuration.

`submitQuestReview` accepts one immutable receipt per assignment. A globally unique request/receipt ID permits an exact replay and rejects reuse for another actor, scope, assignment or decision. Current access and reviewer eligibility are rechecked before a replay is returned. The new receipt and automatic mentor allocation share one atomic transaction. An approved assigned-mentor receipt yields only the domain's mastery/XP **eligibility**; no pass, numerical XP, award or later-quest prerequisite is written. A request for revision retains its original cycle and receipt; revision/retry policy is deliberately unavailable.

## Required adapter contract

`QuestReviewRepository.transaction` must atomically commit or roll back all writes, serialize the **complete cohort/quest peer graph across learners**, and lock/recheck the relevant identity, active membership, eligibility, policy and evidence records. Per-cycle locking is insufficient: simultaneous opposite peer allocations can otherwise create a reciprocal pair. Receipt/request identity must serialize globally across scopes, with database uniqueness for the initial learner/cohort/quest scope, assignment identity, assigned-review receipt and request ID. Store the cycle, policy, assignments and receipts as immutable records. Resolve `subjectId` to the actor using trusted authentication; none of the context booleans or candidate lists may come from a browser request.

The injected tests use a synthetic serializing repository with transactional rollback. They exercise service ordering, one-time sampling/reloads, competing reciprocal allocations, missing policy/pools, exact replay/conflicts, actor/evidence removal, mentor chronology and atomic failure/retry. They do **not** validate PostgreSQL locks, SQL/RLS privileges, persisted bytes after process restart, Supabase, delivery, a real queue or browser behavior. A production adapter requires separate database integration and concurrency tests before this seam can be enabled.

## Configuration and integration still required

- Authored per-quest bank, verified bank/evidence source, accepted evidence format and an explicit sampler/rubric implementation. The sampler must match the configured version and return exactly five distinct bank IDs. Test bank/policy values are synthetic fixtures, never defaults.
- Explicit peer count; trusted peer/mentor eligibility and ranking resolvers; initial assignment trigger permission. This slice supplies no schedule, background retry, reassignment, reroll limit, review retry, revision/invalidation or historical-access policy. Rechecking a still-unassigned initial cycle is caller-triggered and requires current explicit trigger permission.
- Reviewed SQL schema/least-privilege adapter, package/API integration and authorized queue consumers. Missing values or contracts remain unavailable. No new credentials, roles or service are created.
- Quest mastery persistence and XP award/reversal rules, including numeric values, remain separate work. Scheduled access stays in `questReleaseAccess`; review eligibility is never consulted to open a later scheduled quest. The approved 31-day course and three-member projects are unchanged and do not generate dates or affect Raid behavior.

No database was connected or changed, no migration was registered/applied, no curriculum was published, and no live access was granted by this milestone.
