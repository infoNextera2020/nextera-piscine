## Facts that cannot be normalized away

Input is a whole-line protocol. Never apply output-style whitespace normalization to stdin. The provided helper removes LF/CRLF endings while preserving other whitespace and returns a final unterminated line once. Blank input is `"", true`; unavailable input is `"", false`. Scanner overflow can end reading and arbitrary-size recovery is outside the learner task. Retain the source's proposed boundary of at most 20 characters per assessed input line; amounts of six through 20 characters are invalid, not permitted numeric amounts.

## Minimal comparison policy preserving flexible phrasing

1. Keep submitted source bytes and scenario stdin bytes exact and bind any future execution evidence to the same submitted source digest. Supply a finite complete scenario. The existing platform resource contract must be reviewed/published separately; this proposal invents no resource numbers.
2. On output only, canonicalize CRLF/LF line endings and ignore terminal line-ending choice, line-edge horizontal whitespace and extra blank lines when judging prose presentation. Do not collapse all words/digits together, reorder events, drop signs/decimal points, or erase contradictions. Do not strip arbitrary ANSI/control sequences to turn misleading output into a correct observation.
3. Judge the required semantic observation at the relevant step: access to the menu, a clearly identified current balance, a clear rejection and return to menu, or termination without a pending operation. Compare balances as integer values in invented units rather than as a complete literal line. Never accept `100` merely because it appears inside `1000`, a PIN, a menu, a limit, an echoed input or a successful-looking stale balance. Prompts can contain digits; collecting every number in a transcript is not a valid state oracle.
4. Preserve the brief's freedom over wording. Do not require `Balance:`, `Invalid amount`, `Goodbye`, JSON, sentinel tags, exact prompt counts, fixed capitalization or a full golden transcript. Do not require a new balance after every operation or a final balance on exit; explicitly request option `1` when a scenario needs to observe state. A visible rejection is required where the brief asks for a short explanation, but no particular error sentence is mandated.
5. A generic automatic detector cannot prove arbitrary natural-language meaning from arbitrary output. If a detector cannot unambiguously identify the required observation, record comparison as **unresolved**, not automatic PASS or automatic failure for a missing invented phrase. Mentor review of the same immutable attempt can assess that semantic fact. This is an oracle gap that must be closed before enabling automatic evaluation; local demonstration does not bypass the platform's existing automated-result requirement.
6. If future automatic grading needs a narrower output convention, first publish the smallest explicit learner-visible convention and review that substantive restriction against the promised wording flexibility. Do not silently enforce a hidden label/marker or claim that normalization already solves the ambiguity. No new owner judgment about punctuation or exact English messages is needed under the present proposal.
