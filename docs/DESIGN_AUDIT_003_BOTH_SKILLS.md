## How both guides work together

1. **Dickwu: review the task and foundations first.** Audit hierarchy, alignment/grouping, readable type, semantic color, target sizes, keyboard/text scaling, feedback and disclosure. This is a React web portal, so native iOS tab placement, macOS menus, points-to-CSS-pixel equivalence, SF font downloads and Liquid Glass are not mandatory web requirements.
2. **Emil: make the components and motion precise.** Reuse the existing token system, choose feedback by purpose and frequency, keep transitions interruptible, avoid animating frequent navigation or keyboard actions, and gate pointer-only effects. Preserve approved autoplay artwork with pause, visibility and reduced-motion handling; the owner's explicit artwork decision takes priority over general decorative-motion advice.
3. **One implementation plan.** Changes require a task reason, shared type/spacing/color/component tokens and an explicit state inventory. Accessibility/readability comes before polish. New layouts or artwork changes still require the existing review process. The two guides are complementary review criteria, not two competing page generators.
4. **One verification plan.** Review actual composed routes across width and height, 200% text/zoom, keyboard/touch, long content, reduced motion and contrast preferences. Record source, fixture-browser and live-backend evidence separately.

- One prominent next action; quieter feedback and progress context.
- Resources are available through descriptive disclosure rather than removed.
- Existing React components, real content, server-owned actions and truthful unavailable states remain intact.
- X01, emerald and the two approved artworks distinguish 01 coding without relying on generic glass effects.
- Source has visible keyboard focus, >=44px button/summary minimums and explicit reduced-motion handling. Earlier actual fixture checks observed no horizontal overflow at 1440/768/390/320 widths; those are historical checks, not a newly repeated test or all-device guarantee.
